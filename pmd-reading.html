Reading the Chair: The Bench Method

Everything in this section was learned by listening. This page teaches the listening: how the parts of a power chair talk to each other on its control bus, how to hear that traffic with an ordinary computer, and how the chair’s configuration protocol was decoded from captured dealer-tool sessions. Education, step by step — the same way every finding on this site is made.

The rule of the bench: listen first, transmit never. Every procedure on this page is read-only. The computer sends nothing onto the chair’s bus — not even the tiny acknowledgement bits a CAN device normally sends. The chair never knows you are there.

The safety fact, first

The chair’s 4-pin bus cable carries unregulated 24-volt battery power on the same connector as the data wires. That is the one way this work can hurt your equipment: bridge the battery line into a data line, or plug in a non-isolated adapter, and a wiring fault can travel straight up the USB cable into your computer.

So: only ever connect through a galvanically isolated USB-to-CAN adapter (isolation rated 2500V or better) — an adapter with a built-in electrical barrier between the chair side and the computer side — and only in listen-only mode. No exceptions, including “just for a second.”

What you need

  • A computer running Linux. Linux has CAN support built in (called SocketCAN) — the adapter appears as a network-style interface named can0.
  • An isolated USB-to-CAN adapter (the gs_usb / CANable class of device), for the reason above.
  • Your own chair, and time. Nothing here is done to anyone else’s chair, and nothing here changes yours.

Open question, marked honestly: the R-net bus uses fault-tolerant CAN transceivers. Which adapter transceivers are fully compatible with that bus must be confirmed on the bench before anything is connected to a live chair — the project’s own first bench session is pending hardware, and its results will be recorded here from the real session. Terminal output is never written in advance on this site.

Procedure B1 — See what is plugged in

  1. Plug the isolated adapter into the computer. Nothing is connected to the chair yet.
  2. Ask the computer what it sees. The first command lists every USB device; the second asks whether the CAN interface exists yet:
lsusb -v | grep -E "idVendor|idProduct|iManufacturer|iProduct"
ip -details link show can0

How you know it worked: the USB list shows the adapter as a named device, and the second command prints details for can0 instead of an error.

Procedure B2 — Listen without saying anything

  1. Connect the adapter to the chair’s bus cable — isolated adapter only, battery line never bridged to a data line.
  2. Set the interface to the bus speed, listen-only, and bring it up. Every device on a CAN bus must agree on the speed or nothing can be read; we measured this bus at 125000 (125 kbps) on the bench:
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 125000 listen-only on
sudo ip link set can0 up
  1. Record the traffic while you trigger a fault you already understand — flip a freewheel lever, or unplug the charger (see the cheap fixes). The log then contains a fault you can recognize, timestamped, next to the traffic that carried it:
candump -tz -l can0

How you know it worked: the log fills with timestamped frames, including new traffic at the moment you triggered the fault — and the chair behaves completely normally the whole time, because the computer only listened.

What the traffic taught us

This is how the findings on the PMD page were made. Dealer programming sessions were captured on the bus and decoded offline. The chair’s configuration moves as data objects, each protected by a checksum — a number that proves the data arrived unchanged. Sixteen configuration objects were read straight off the bus in those captures. Decoding the read path showed there is no encryption and no cryptographic authentication on the bus: the barrier is that the manufacturer’s software will not open its dealer settings unless its own dongle is plugged in — and the dongle itself is a plain FTDI FT232 USB-to-serial bridge, an ordinary adapter chip.

What this page does not teach, because it is not proven: writing a configuration back. The shortcut the community assumes — that a configuration file’s layout maps directly onto live bus addresses — is contradicted by the project’s own captures. A restore procedure will be published here when it has been proven on a live power module on the bench, and not before. That is this site’s standard, and it is not negotiable: proven today is read, backup, and understanding.
