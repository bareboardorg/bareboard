Reading the Chair: The Bench Method

Everything in this section was learned by listening. This page teaches the listening: how the parts of a power chair talk to each other on its control bus, how to hear that traffic with an ordinary computer, and how the chair’s configuration protocol was decoded from captured dealer-tool sessions. Education, step by step — the same way every finding on this site is made.

The rule of the bench: listen first, transmit never. Every procedure on this page is read-only. The computer sends nothing onto the chair’s bus — not even the tiny acknowledgement bits a CAN device normally sends. The chair never knows you are there.

The safety fact, first

The chair’s 4-pin bus cable carries unregulated 24-volt battery power on the same connector as the data wires. That is the one way this work can hurt your equipment: bridge the battery line into a data line, or plug in a non-isolated adapter, and a wiring fault can travel straight up the USB cable into your computer.

So: only ever connect through a galvanically isolated USB-to-CAN adapter (isolation rated 2500V or better) — an adapter with a built-in electrical barrier between the chair side and the computer side — and only in listen-only mode. No exceptions, including “just for a second.”

The parts you need — and how they connect

Three things. Each one is defined here, in the order you will touch them.

  • A computer running Linux. Linux is a free operating system (the software that runs the computer, like Windows or macOS). It has CAN support built in, called SocketCAN: once the adapter below is plugged in, the computer treats it as an interface named can0 — can for the network, 0 because it is the first one.
  • An isolated USB-to-CAN adapter (a gs_usb-compatible model with galvanic isolation; not every CANable-class board is isolated, so check the exact model). This small box translates between the computer’s USB port and the chair’s wiring. Isolated means it has a built-in electrical barrier between its two sides, so a fault on the chair’s 24 volts cannot travel into the computer. One end of the adapter is a USB plug, for the computer. The other end is where the chair’s wires land.
  • The chair’s bus cable. The bus is the chair’s internal wiring network — the cables the joystick, the power module, and the seating module use to talk to each other. Its plugs are round, with 4 pins. The cable runs from the back of the joystick down to the power module in the base.

How they connect, in plain words: computer → (USB cable) → adapter → (the adapter’s chair-side wires) → the chair’s bus cable. The adapter sits between the computer and the chair and only listens. Procedure B1 below connects only the computer half, first. Procedure B2 makes the chair connection, in listen-only mode.

Open question, marked honestly: the R-net bus uses fault-tolerant CAN transceivers (a transceiver is the chip that speaks onto the wires). Which adapter transceivers are fully compatible with that bus must be confirmed on the bench before anything is connected to a live chair — the project’s own first bench session is pending hardware, and its results will be recorded here from the real session. Terminal output is never written in advance on this site.

Procedure B1 — See what is plugged in

  1. Plug the isolated adapter into the computer. Nothing is connected to the chair yet.
  2. Ask the computer what it sees. You type commands into a terminal — a plain window that takes typed instructions and prints text answers. In the boxes on this page, lines starting with $ are lines you type exactly as shown (the $ itself is the computer’s prompt — do not type it), and you press Enter after each line. The first command lists every USB device; the second asks whether the CAN interface exists yet:
$ lsusb -v | grep -E "idVendor|idProduct|iManufacturer|iProduct"
$ ip -details link show can0

How you know it worked: the USB list shows the adapter as a named device, and the second command prints details for can0 instead of an error.

Procedure B2 — Listen without saying anything

  1. STOP — do not connect to a live chair yet. The project has not confirmed which adapter transceivers are compatible with the R-net bus’s fault-tolerant CAN. Do not use this procedure on a live chair until this page names the confirmed adapter and its exact pin connections. (The steps below are the procedure as it will run, published for review.)
  2. Set the interface to the bus speed, listen-only, and bring it up. Every device on a CAN bus must agree on the speed or nothing can be read; the project’s captured dealer-tool sessions used 125000 (125 kbps):
$ sudo ip link set can0 down
$ sudo ip link set can0 type can bitrate 125000 listen-only on
$ sudo ip link set can0 up
  1. Record the traffic while you trigger a fault you already understand — with the chair unoccupied, on level ground, and its drive wheels blocked — flip a freewheel lever, or unplug the charger (see the cheap fixes). The log then contains a fault you can recognize, timestamped, next to the traffic that carried it:
$ candump -tz -l can0

How you know it worked: the log fills with timestamped frames, including new traffic at the moment you triggered the fault — and the chair behaves completely normally the whole time, because the computer only listened.

Your phone: what it can and cannot do

Your phone is a documentation tool in this work — a camera, a light, and a notebook. It is not a bus tool. Here is the honest split, phone by phone, with every step spelled out.

Both phones

  • Photograph the fault before you touch anything. Open the Camera app, point it at the joystick screen or the flashing lights, tap the screen once to focus, and take the photo. On R-net chairs, photograph the screen showing the code. On VR2 and LiNX chairs, take a short video instead — a 10-second clip captures the flash count exactly, and you can count it as many times as you need.
  • Use the flashlight to inspect. The charger-socket cleaning (Procedure 2) and the connector inspection (Procedure 4) both start with looking closely. iPhone: swipe down from the top of the screen to open Control Center, then tap the flashlight icon. Samsung: swipe down from the top to open Quick Settings, then tap the flashlight tile. Swipe or press Home to leave it on while you work.
  • Photograph wiring before you disconnect it. Procedure 3 (batteries) depends on this: the photo is what you rewire from. Take it before the first bolt moves.
  • Keep the record on the phone. The photos, the codes you wrote down, and a copy of your chair’s backup file belong together. iPhone: the Files app. Samsung: the My Files app. Name the folder with your chair’s model and the date.
  • LiNX chairs: the manufacturer’s programming tool does not open the lock either. Dynamic Controls publishes the free LiNX Access tool for iOS and PC; it is not the Android app. (MyLiNX is the separate Android app.) Without an authorised LiNX Access Key — DLX-HKEY01-A (distributor/dealer) or DLX-HKEY02-A (manufacturer), plugged into the remote’s charger/programming (3-pin XLR) port — the tool cannot connect to a live chair to read the detailed fault log or the settings. Without the key, it can still open a stored configuration file at the default, read-only level. The lock reaches the phone too.

iPhone: what it cannot do

An iPhone cannot listen to the bus. There is no way to connect the CAN adapter to it that iOS will allow an app to use — this is a limit of the phone’s system, not a missing app. Reading the bus takes the computer.

Samsung (Android): what it cannot do

Android has a free terminal app called Termux that gives you the same kind of type-a-command window as the computer. But on a normal, unmodified Samsung phone, plugging the adapter in does not create the can0 interface — the phone’s system does not ship with that support turned on, and no app can add it. Any guide that tells you otherwise is skipping the part where it does not work. The phone documents; the computer listens.

What the traffic taught us

This is how the findings on the PMD page were made. Dealer programming sessions were captured on the bus and decoded offline. The chair’s configuration moves as data objects, each protected by a checksum — a number that proves the data arrived unchanged. Sixteen configuration objects were read straight off the bus in those captures. Decoding the read path showed there is no encryption and no cryptographic authentication on the bus: the barrier is that the manufacturer’s software will not open its dealer settings unless its own dongle is plugged in. The project record contains incompatible accounts of what is inside that dongle, so its internal hardware is not stated as settled fact here.

What this page does not teach, because it is not proven: writing a configuration back. The shortcut the community assumes — that a configuration file’s layout maps directly onto live bus addresses — is contradicted by the project’s own captures. A restore procedure will be published here when it has been proven on a live power module on the bench, and not before. That is this site’s standard, and it is not negotiable: proven today is reading captured dealer-tool sessions and understanding them; owner-adapter backup is not yet proven.
